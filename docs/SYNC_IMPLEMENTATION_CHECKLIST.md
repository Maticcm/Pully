# Playlist synchronization implementation checklist

Status as of this change. “Implemented” does not imply real-provider verification.

- [x] yt-dlp subscriptions, queue integration, fixed and custom intervals, pause/resume, manual sync and removal. Automated build checks only; end-to-end behavior remains unverified.
- [x] Persist configuration and last 50 run outcomes; recover in-memory job state on restart. Serialization and bounded-history unit tests pass; active-process restart is unverified.
- [x] Preserve sync data and disable sync writes if state is unreadable or only a backup can be read. Unit coverage is limited to the backup case.
- [x] yt-dlp download archive skips recorded items. No integration test has established behavior for all provider failures or file changes.
- [ ] Spotify subscriptions use SpotiFLAC playlist mode without a Spotify token. Live metadata checks returned complete track-ID snapshots, including 23 tracks for the user-provided playlist; comparisons for additions, removals and reordering pass fixture tests. A clean direct CLI download test encountered a provider challenge and repeated timeouts, so a completed audio sync through Pully remains unverified. Changed real playlists and restart recovery remain unverified. SpotiFLAC de-duplicates repeated tracks in its playlist output.
- [ ] Playlist snapshots detect additions, removals and relative reordering; tracked paths allow missing-file retry and optional M3U8 output. Fixture tests cover comparison, archive edits and M3U ordering; full app integration and real playlist downloads remain unverified. Files downloaded before path tracking may not be mapped. Change summaries are not yet preserved per history entry.
- [ ] Verify duplicate prevention, cancellation, network interruption, overlapping jobs, shutdown and crash recovery using realistic integration tests and live providers.
- [x] A pending playlist snapshot is committed only after a successful job; terminal sync jobs cannot be removed before their result is saved. The Windows provider process is attached to a kill-on-close job object, and a guard-drop test verifies child termination. An interrupted or failed run must still be exercised end to end.
- [x] Pending provider results are checked for missing or duplicate track IDs, and skipped results must point to verified local FLAC files. SpotiFLAC can merge distinct Spotify IDs for the same recording, so its plan is not assumed to have the same count as the Spotify snapshot. This validation has fixture coverage but has not yet been exercised on a successful live download.
- [x] An offline exercise of the installed SpotiFLAC 5.0.6 planner with generated FLAC files verified that an unchanged playlist skips both tracks, reordering changes the M3U order, and deleting one file schedules that track again. This tests the upstream planner directly, not a complete Pully sync.
- [x] The Spotify sync worker reports progress from the CLI's track-start messages and checks that the M3U named in the current CLI summary contains valid local files. Fixture tests cover progress parsing, stale playlist rejection and invalid paths; end-to-end UI progress remains unverified.
- [x] Spotify share and localized playlist URLs are normalized for new subscriptions, including duplicate detection against existing subscriptions and equivalent destination paths. The CLI compatibility probe exercises the separate subscription and backfill parsers in an isolated database; it does not assume those commands appear in the main help.
- [x] The Spotify worker drains both output streams concurrently, waits for the main process before closing its process-tree guard, and enforces an overall timeout sized for the playlist. A Windows process test covers a stalled child; cancellation and descendant-pipe handling still need end-to-end testing.
- [x] The real SpotiFLAC CLI processed the user's 23-track playlist against locally generated silent FLAC fixtures, skipped all tracks and wrote an M3U; Pully's parser and FFprobe validation accepted its output. Removing one fixture with an intentionally unavailable provider produced a zero-exit incomplete report, which Pully rejected. This is not a real audio-download test. The fixture check is `real_spotiflac_playlist_output_passes_validation` with `PULLY_TEST_SPOTIFLAC_FIXTURE` set to the generated workspace.
- [ ] SpotiFLAC 5.0.6 installed in an isolated environment and exposed the required CLI options; the PATH executable is the incompatible 0.2.8 generation. The public multiline report is parsed, and optional retries, timeout and no-fallback flags are used when advertised. FFprobe validates streams when available. The Pully installer and an authorized download have not been tested end to end; FFprobe does not validate every audio frame.
- [ ] Verify UI in a running desktop window, at multiple sizes, and exercise all sync actions. The computer-use native pipe was unavailable on 2026-11-08 after retry and reset.

Recovery: if `synced-playlists.json` is damaged and `synced-playlists.bak` is valid, close Pully and restore the backup to the JSON filename in the app data directory. Sync is intentionally disabled until this is done to avoid overwriting either file.

## Next verification steps

1. Exercise an authorized public playlist with compatible SpotiFLAC through Pully: first download, repeat without duplicates, delete one tracked file and sync again, then verify the M3U and failures. The live metadata-only test is `live_spotiflac_playlist_snapshots_are_stable` with `PULLY_TEST_SPOTIFLAC` set to a compatible executable.
2. Test modifications to a playlist the tester owns, including removal and reordered distinct tracks, plus a restart while downloads are active. SpotiFLAC deduplicates repeated tracks, so duplicate occurrence changes are not represented.
3. Verify the desktop UI and app-managed installer in a real running app. The previous computer-use helper could not connect to its native pipe.
4. Check process-tree shutdown, provider timeouts, failed-file validation, partial playlists and upstream CLI compatibility under failure.
